## 1. 재현의 목적과 과제 전체 범위

안내서 p.1·3은 원 알고리즘 이해, Table 1의 주요 실험 재현, 논문 결과와의 비교 및 차이 분석을 요구한다. 이어서 원 방법의 한계를 분석하고 자체 개선 알고리즘을 개발해야 한다. 전체 보고서에는 제안 방법과 실험, 분석, 한계, 재현 정보도 포함해야 한다.

우리의 첫 완료 단위는 **원 방법의 재현 표 + 실행 근거 + 차이·한계 분석 + 재현 보고서 초안**이다. 그 뒤에 개선 가설을 선택해 실제 구현·비교 실험을 진행한다. 개선 아이디어만 적는 것으로 과제 전체의 제안 방법·실험 요구를 대신하지 않는다.

사용자가 확정한 재현 규모는 서로 다른 모델 2개, Few-shot·CoT·RePE, LLM-only·LLM-A*와 공통 A*·Dynamic Weighted A*를 합친 14개 조건이다. 각 조건의 평가 대상은 공개 1,000개 문제다. 이는 원 Table 1의 비교 구조를 따르기 위해 선택한 범위이며 안내서가 최소 모델 수를 별도로 지정한 것은 아니다.

## 2. AI 사용과 유사성 검증: 어디까지 명시되어 있는가

### 안내서에 명시된 내용

- **p.4:** AI 도구의 보고서 작성 보조는 허용된다. AI 생성문은 면밀히 검토하고 자기 말로 의미 있게 수정해야 하며, 정확성은 제출자가 책임진다.
- **p.4:** 보고서의 방법·실험·결과는 실제 구현하고 수행한 작업과 일치해야 한다. 검토·수정 없는 AI 생성문, 허구의 결과·참고문헌, 수행하지 않은 실험 설명은 위반이 될 수 있다.
- **p.4:** 공식 LLM-A* 코드를 재현에 사용하고 확장하는 것이 허용된다. 외부 코드와 자료는 보고서에서 명확히 인용해야 한다.
- **p.6:** 제출물 사이에 상당한 유사성이 있거나 복사가 의심되면 추가 검증을 요구할 수 있다. 코드 수정 이력, 실험 기록, 구두 설명이 예시로 제시되어 있다.
- **p.6:** 다른 학생·팀의 보고서, 실험 결과, 분석, 작성 내용을 복사하는 것을 금지한다. 팀 제출 보고서는 해당 팀이 독립적으로 작성해야 한다.

### 안내서만으로 알 수 없는 내용

- 특정 AI 탐지기 또는 코드·문장 유사도 검사 도구의 사용 여부와 이름.
- 판정에 쓰이는 점수나 유사도 기준치.
- 검사 대상 파일이나 보고서 절의 정확한 범위.
- 논문 재현 부분을 검사에서 제외한다는 규정.
- AI 코딩 도구의 사용 방식별 세부 허용·금지 범위.

따라서 **재현 부분도 추가 검증의 근거를 제시할 수 있게 준비하되, 실제 검사 범위나 통과 여부를 단정하지 않는다.** AI 보고서 보조를 허용한 조항만으로 다른 모든 AI 활용 방식까지 명시적으로 허용되었다고 말하지 않는다. 별도 공지나 TA 답변이 있으면 반영한다.

### 이번 작업에 적용하는 방식

같은 논문의 수식, 알고리즘 순서, 원 프롬프트와 인용한 공식 코드를 사용하는 것은 재현 목적에 부합한다고 해석할 수 있다. 실제 검사 판정은 이 문서가 보장하지 않는다. 외형적인 차이를 만들기 위해 재현 알고리즘을 바꾸는 대신, 출처를 밝히고 직접 실행한 결과를 해석한다.

각 표의 수치가 어떤 코드 커밋·설정·LLM 응답·실행 기록에서 나왔는지 추적할 수 있게 한다. 원본 코드, 실행 호환을 위한 수정, 우리 평가 코드, 이후 제안 알고리즘을 구분한다. 보고서는 결과를 본 뒤 작성하고, 사용자가 내용을 이해하고 자신의 말로 검토·수정한다.

AI가 도운 작업과 사람이 확인한 내용을 짧게 기록하는 것은 우리 측 권장 운영 방식이다. 안내서가 별도의 AI 사용 보고서나 특정 공개 양식을 요구한 것은 아니다. 팀 기술 기록과 개인 기여 보고서는 구분하고, 개인 기여 보고서는 팀원과 논의·공유하지 않는다.

## 4. 추가점수 가능 항목과 실험 설계

안내서 p.3은 다음에 추가점수를 줄 수 있다고 명시하며, 점수나 보상 여부를 보장하지 않는다. 필수 재현·제안 실험이 먼저다.

1. **다른 LLM 또는 새 환경의 일반화:** 두 모델 사이에서 효과가 유지되는지 비교하고, 원 실험 이후에는 새 맵 크기·장애물 배치·밀도에서도 확인한다. 두 모델을 실행했다는 사실만으로 가점을 확정하지 않는다. 방법을 고른 데이터와 최종 평가 데이터를 구분한다.
2. **명확한 수식·의사코드·그림:** waypoint와 실제 경로, 탐색 영역, target 전환을 보여준다. 원 방법과 제안 방법의 바뀐 부분을 독자가 따라갈 수 있게 표시한다.
3. **잘 설명한 실패 실험과 비용 효율:** 실패 사례를 분류하고 원인과 재현 조건을 남긴다. operation 감소와 실제 시간 감소를 구분하고 LLM 생성 비용·지연, 탐색 시간, 캐시 재생 시간을 각각 설명한다.

추가로 같은 응답을 이용한 `target=goal` 대조군, 맵 단위 불확실성 분석, 프롬프트 예시 중복 분석을 수행할 계획이다. 이는 우리 분석 설계이며 안내서가 이 세 실험을 필수로 지정한 것은 아니다.

## 5. 한계에서 개선점으로 연결하는 기록 방식

각 항목을 `관측 → 원인 가설 → 확인 실험 → 개선 후보 → 검증 결과` 순서로 남긴다. 아래는 앞으로 검증할 예시이며 현재 입증된 성능 결과가 아니다.

- 잘못된 waypoint에서 탐색량 증가가 관측되면, 동일 입력과 응답으로 target=goal 대조군을 실행해 안내의 영향을 확인한 뒤 안내 강도·중단 조건을 검토한다.
- operation은 줄지만 시간이 늘면, OPEN 재계산과 LLM 지연을 나눠 측정한 뒤 실제 병목에 맞는 개선을 검토한다.
- 파싱 실패가 많으면, 원문 응답과 추출 단계의 문제를 구분한다. API/parser 호환 수정의 효과와 새 탐색 알고리즘의 효과는 별도로 평가한다.

사용자는 구현 단계마다 대표 사례 하나를 따라가며 f 계산, target 전환, 경로 복원, 실패 집계와 표의 수치가 나오는 과정을 설명해 본다. 이는 학습과 검증을 위한 우리 절차이며 안내서가 별도 구두시험 일정을 확정한 것은 아니다.
